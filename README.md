# صارح

منصة رسائل عربية مبنية على Next.js 16 وTypeScript وSupabase Auth وPostgreSQL وStorage وRealtime. Supabase Auth هو المسؤول عن كلمات المرور والاستعادة؛ لا نخزن كلمات مرور في جداول المشروع.

## Supabase والإعداد المحلي

1. أنشئ مشروع Supabase جديدًا.
2. لمشروع جديد: شغّل `supabase/schema.sql` مرة واحدة. لمشروعك الحالي الذي شغّلت عليه المخطط الأول: شغّل فقط `supabase/migrations/20261103010000_private_conversations.sql` من SQL Editor؛ لا تعِد تشغيل المخطط الأول.
   إذا كان جدول `profiles` فارغًا رغم وجود مستخدمين في Auth، شغّل `supabase/repair_missing_profiles.sql` مرة واحدة لإصلاح الحسابات الموجودة وإعادة تثبيت trigger الملفات الشخصية.
3. انسخ `.env.example` إلى `.env.local` واملأ القيم. لا تضع مفتاح الخدمة في متغير يبدأ بـ `NEXT_PUBLIC_`.
4. في Supabase Auth → URL Configuration، اضبط Site URL وأضف `http://localhost:3000/auth/callback` و`http://localhost:3000/reset-password` وعناوين النطاق الإنتاجي إلى Redirect URLs.
5. شغّل `npm install` ثم `npm run dev`.

`ANON_MESSAGE_HASH_SECRET` يجب أن يكون سرًا عشوائيًا طويلًا. يمكن توليده باستخدام `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`. الخادم يستخدم HMAC لبصمة مؤقتة لأغراض الحد من الإرسال، ولا يحفظ عنوان IP نفسه في سجل الرسالة. حد الإرسال الحالي 5 محاولات لكل بصمة في نافذة 10 دقائق.

للحماية من البوتات، أنشئ مفاتيح Cloudflare Turnstile وأضف Site Key وSecret Key. التحقق من Secret يتم على الخادم فقط. عند ضبط Secret يصبح التحدي مطلوبًا قبل إرسال الرسالة.

## الأسرار ومتغيرات البيئة

- `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`: تستخدمهما الواجهة مع RLS. يقبل المشروع أيضًا المفتاح القديم `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
- `SUPABASE_SECRET_KEY`: خادم Next.js فقط لإرسال الرسائل المجهولة بعد التحقق والحد من المعدل؛ ممنوع وضعه في المتصفح أو تسميته ببادئة `NEXT_PUBLIC_`. يقبل المشروع المفتاح القديم `SUPABASE_SERVICE_ROLE_KEY` أيضًا.
- `ANON_MESSAGE_HASH_SECRET`: سر HMAC للخادم فقط.
- `NEXT_PUBLIC_TURNSTILE_SITE_KEY` و`TURNSTILE_SECRET_KEY`: حماية اختيارية من البوتات، السر يبقى خادميًا.

لا تعرض سياسات RLS الرسائل للزوار. إدخال الرسائل متاح حصريًا عبر `POST /api/messages` الذي يتحقق من الأصل، والمدخلات، واستقبال الملف، وTurnstile عند ضبطه، ومحدد المعدل في Postgres. لا تستخدم قاعدة بيانات محلية أو phpMyAdmin للإنتاج.

## النشر على Vercel

استورد المشروع في Vercel وأضف المتغيرات السابقة في Environment Variables للنطاقات المطلوبة، ثم أضف نطاق Vercel إلى Supabase Auth Redirect URLs وأعد النشر. اسمح بمفتاح الخدمة فقط في بيئات الخادم في Vercel. أنشئ Turnstile لموقعي المحلي والإنتاج أو النطاقات المناسبة لهما.

## الوظائف والبنية الموجودة

- التسجيل وتسجيل الدخول وتأكيد البريد واستعادة كلمة المرور عبر Supabase Auth.
- ملفات عامة، ورسائل مجهولة عبر API خادمي، ومحادثات خاصة للردود مرتبطة بمفتاح متابعة عشوائي محفوظ على جهاز المرسل، وRate limit ذري في Postgres.
- لوحة رسائل مع البحث، والحذف، وتحديد القراءة، والمفضلة، والتثبيت، والاشتراك في Supabase Realtime للرسائل والإشعارات.
- RLS للملفات والرسائل والمفضلة والإشعارات والبلاغات والحظر وصلاحيات الإدارة. بيانات الحساب الخاصة موجودة في Auth ولا ترجع ضمن الملف العام.
- Storage bucket عام لصور الحساب، مع سياسات تقيّد رفع/تعديل/حذف الملفات بمجلد صاحب الحساب، وbucket خاص لمرفقات الرسائل لا يمكن قراءته إلا عبر مسار تحقق للمحادثة.
- رفع صورة الحساب اختياري من الإعدادات. الرسائل تدعم الصور ومعاينتها، والردود النصية والصور، وتعديل/حذف النصوص فقط. رسائل الصور غير قابلة للتعديل أو الحذف.
- جداول وتقسيم صلاحيات أساسي للبلاغات والمديرين، دون تهيئة أول مدير تلقائيًا.

قبل فتح الموقع للعامة، راجع نصوص الخصوصية وفق سياسة خدمتك، اضبط البريد في Supabase، فعّل مفاتيح Turnstile، وعيّن أول مدير يدويًا من SQL موثوق. لم تُنفذ بعد واجهة إدارة البلاغات والمستخدمين، وإجراء الحظر من لوحة المستخدم، وحذف الحساب، وتعديل البريد والهاتف.

## التحقق المحلي

```bash
npm run lint
npm run build
```

لم يجر اتصال فعلي بمشروع Supabase ضمن بيئة التطوير لعدم توفر بيانات مشروعك. بعد إدخال بياناتك وتشغيل SQL، اختبر تسجيل حساب، تأكيد البريد، الرسالة المجهولة، ظهورها في لوحة المالك، تحديث Realtime، والاستعادة من البريد.
